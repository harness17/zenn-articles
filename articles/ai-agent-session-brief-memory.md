## はじめに

Codex や Claude Code に長期記憶を持たせると、前回の判断や作業方針を引き継ぎやすくなります。自分も Obsidian 風の Markdown vault に、設計判断、戦略メモ、handoff、現在の目標を残す運用をしていました。

ここでいう Codex は、ローカルリポジトリを読み書きしながら作業できる OpenAI のコーディングエージェントです。Claude Code と同じく、ファイルとして残した文脈を次の作業に使う前提で扱っています。

ただ、記憶を増やすほど別の問題が出ました。起動時に読むファイルが大きくなり、作業そのものよりも「過去ログを毎回読むこと」にコンテキストを使うようになったのです。

この記事では、AI エージェント用の長期記憶を増やすだけでなく、起動入口を `session-brief` に分けて軽く保つようにした話を書きます。対象読者は、AI コーディングエージェントに継続的な文脈を持たせたいが、コンテキスト肥大に困っている個人開発者です。

関連する記事管理の実例は [harness17/zenn-articles](https://github.com/harness17/zenn-articles) に置いています。この記事では、非公開 vault の中身そのものではなく、公開しても問題ない運用パターンだけを扱います。

## 記憶を増やすほど起動が重くなった

最初は、長期記憶を単純に増やせばよいと考えていました。

- 現在の目標を `goals.md` に書く
- 設計判断を `decisions/` に残す
- 戦略メモを `strategies/` に残す
- Codex と Claude Code の引き継ぎを `handoffs/` に残す

この構成自体は役に立ちました。前回なぜその設計にしたか、どの記事が公開待ちか、どの作業を別エージェントに渡したかを、会話ログだけに閉じずに追えるようになりました。

一方で、起動時に読む入口を増やしすぎると、別の負荷が出ます。`goals.md` に完了済み履歴まで残り、`decisions/index.md` に全件索引が入り、handoff も古いものを直下に置いたままにすると、毎回の orientation が重くなります。

実際に運用していたときは、`goals.md` が約 36KB、`decisions/index.md` が約 11KB まで膨らみました。内容は有用でも、毎セッションの最初に全文を読むには大きすぎます。長期記憶を持たせたはずが、直近タスクに使える余白を減らしていました。

## session-briefを起動入口にした

そこで、起動時に読むファイルを `session-brief` に分けました。

`session-brief` は、詳細履歴ではなく「どこを入口に読むか」を示す薄いブリーフです。現在の焦点、読み取り方針、圧縮メンテナンス基準だけを置き、必要なときだけ詳細ノートへ進む形にしました。

```markdown
# session-brief

## 読み取り方針

- 起動時の基本入口はこのファイル、reminders、必要なら goals の先頭のみ。
- goals、decisions/index、handoffs は全文展開しない。
- 目的に合うリンクや直近ファイルだけ読む。
- セッションログ調査は構造化抽出し、巨大な検索結果を会話へ流さない。

## 現在の焦点

- 記事と公開後確認
- 個人開発アプリの配布導線
- Skill Graph の軽量維持
```

ここで重要だったのは、`session-brief` を「要約の置き場」にしすぎないことです。要約を厚くしすぎると、また起動入口が肥大化します。

本文には詳細を書かず、詳細が必要な作業だけリンク先を読む。これを徹底したことで、起動時の読み取り量を抑えつつ、古い判断を消さずに済むようになりました。

## 削除ではなくarchiveへ逃がした

コンテキストを軽くするだけなら、古い履歴を削除する方法もあります。ただ、自分の目的は「忘れること」ではありません。後から、なぜその判断をしたのか、どの記事がどの技術領域を示すのかを説明できる状態にすることです。

そのため、削除ではなく archive に逃がす方針にしました。

```text
memory/
├── self/
│   ├── session-brief.md   # 起動入口
│   └── goals.md           # アクティブ中心
├── decisions/
│   └── index.md           # 軽量な map
├── ops/
│   └── handoffs/          # 直近・継続中だけ
└── archive/
    ├── goals/             # 完了済み履歴
    ├── decisions/         # 全件索引や古い詳細
    └── handoffs/          # 完了済み handoff
```

この整理で、`goals.md` は約 36KB から約 2KB、`decisions/index.md` は約 11KB から約 2.5KB まで縮みました。

数値が小さくなったこと自体より、入口の役割が明確になったことの方が大きいです。起動時は「今見るもの」だけを読み、過去の詳細は検索やリンクから取りに行く。長期記憶と毎回の作業コンテキストを分けられました。

## 起動時に読まないものを決めた

圧縮後にもう一つ決めたのは、「起動時に読まないもの」です。

AI エージェント向けの記憶運用では、何を読むかより、何を毎回読ませないかが重要でした。自分は次のように分けています。

| 種類 | 起動時の扱い | 必要になったとき |
| --- | --- | --- |
| `session-brief` | 読む | 常に入口として使う |
| reminders | 読む | 期限確認に使う |
| goals | 必要な先頭だけ読む | 現在タスクが関係するときに詳細を読む |
| decisions/index | 全文展開しない | 関連判断を検索して読む |
| handoff | 直近だけ見る | 継続作業やレビュー時に対象だけ読む |
| session logs | 読まない | 調査時だけ構造化して抽出する |

この分け方にしてから、古い情報に引っ張られて現在の作業がぼやけることも減りました。

長期記憶は、毎回全部読ませるためのものではありません。検索でき、必要なときに取り出せる状態であればよい。ここを分けないと、記憶を増やすほど作業が重くなります。

:::message
公開記事や公開リポジトリにこの運用を書くときは、vault の実パス、個人事情、就職活動の詳細、非公開プロジェクト名をそのまま出さないようにしています。長期記憶の構造は共有できますが、中身は公開物ではありません。
:::

## 圧縮トリガーをルール化した

一度軽くしても、運用していればまた増えます。そのため、圧縮するタイミングもルールにしました。

```markdown
## 圧縮メンテナンス基準

- goals.md が 8KB を超えたら、完了済み履歴を archive/goals/ へ移す。
- decisions/index.md が 8KB を超えたら、全件索引を archive/decisions/ へ退避する。
- handoffs/ 直下は直近・継続中だけ残す。
- 詳細な履歴は goals に追記せず、decision / strategy / archive に分ける。
```

この基準は厳密な性能チューニングではなく、運用上の警戒ラインです。ファイルサイズが 8KB を超えたら必ず壊れる、という意味ではありません。ただ、自分の運用では、それくらいから「起動時に読むには重い」と感じ始めました。

基準を置いておくと、圧縮を思いつきの掃除にしなくて済みます。記事公開が続いた後、複数セッションにまたがる実装が終わった後、handoff が増えた後に、入口だけを見直す判断がしやすくなりました。

## まとめ

AI エージェントの長期記憶は、増やすだけでは扱いづらくなります。

自分の場合は、起動入口を `session-brief` に分け、完了済み履歴や全件索引は archive へ退避しました。起動時に読むもの、読まないもの、必要なときだけ取りに行くものを分けたことで、記憶の検索性と作業時の軽さを両立しやすくなりました。

長期記憶を作るときは、まず「何を残すか」だけでなく、「毎回読ませないために入口をどう薄くするか」を決めるのが効きます。
