## はじめに

個人で Zenn に技術記事を書くとき、Claude Code と Codex CLI を**役割固定でクロスレビュー**させる運用を回しています。本記事は、その運用で実際に拾った指摘パターンと、ハーネス化前に踏んだ失敗の記録です。

対象読者は、AI に記事やコードを書かせているが、公開前レビュー、守秘確認、事実確認を毎回会話だけで済ませていて不安が残る人です。Zenn 記事を例にしていますが、README、技術ブログ、ポートフォリオ説明のレビューにも同じ考え方を使えます。

ここでいう Codex CLI は、旧 Codex 言語モデルではなく、OpenAI の `openai/codex` リポジトリで公開されているローカル実行のコーディングエージェントを指します。

1 台の AI に書かせるだけで公開していた頃、公開後に「ここ事実誤認だった」「締め方が AI 的だった」と気づくことが続きました。同じ AI に「あなたが書いたこの記事をレビューして」と頼んでも、直前のコンテキストに引きずられて自然と判定してしまいます。作成側と別の AI に通すゲートを公開前に必ず置く形に変えたら、自分の盲点が言語化されて残るようになりました。

この記事でいう handoff ファイルは、AI 同士の作業依頼、レビュー結果、未確認事項を時系列で残す共有メモです。ハーネス化は、その handoff、レビュー観点、公開ゲートを毎回の会話ではなくリポジトリ内のルールとテンプレートに固定することを指します。

なお、同シリーズで先行する「Claude Code 運用を数ヶ月で見直して rules と skills に分けた話」では、クロスレビューを**運用変遷の 1 要素**として軽く触れていました。本記事ではそこを単独テーマに切り出し、過去の handoff から拾った指摘パターン 4 種と、ハーネス化前に踏んだ失敗 3 種を一次情報レベルで掘ります。

## なぜ 1 台では足りないのか

自分が書いた記事を自分で校正できないのと同じ構造的問題が、AI 1 台にもあります。書いた直後のコンテキストに沿って読むため、事実誤認・締め文紋切型・宣伝寄りを「自然」と判定します。

実例を 3 つ並べます。

**事実誤認**：ある比較記事で「片方のリポには 1 種類しか存在しない」と主張していました。書いた本人は自己レビューを通しましたが、別 AI に通したところ「現在の既定ブランチには両方の派生が存在する。旧コミットを暗黙参照したまま本文を断言している」と指摘されました。同じ AI に再読させても、最初の前提を引きずる側に寄ります。

**参考リンクの 404**：同じ記事の参考リンクは GitHub の `blob/<既定ブランチ名>` 形式で書かれていましたが、対象リポの既定ブランチ名と食い違っていて全件 404 でした。書いた AI は「一般的な名前だから自然」とだけ判定していました。これも作成者と別の AI が機械的に Git ホスティングの実態を確認したから引っかかりました。

**ドメイン用語の漏れ**：別の記事で、業務ドメイン固有の語彙を含む Enum 名（`DomainSpecificTraining`、`ApplicationProcess` 相当）をサンプルコードに使っていました。書いた AI は「業務カレンダーのサンプルとして自然」と判定しましたが、別 AI が「特定ドメインの語彙が透けている」と検出。`EventCategory.Work / Meeting / Training` のような汎用名に置換しました。

## 役割を固定する（作成者 ≠ レビュアー）

クロスレビューのルールはシンプルです。

- Codex が書いた記事は Claude Code がレビューする
- Claude Code が書いた記事は Codex がレビューする
- 同じ AI が自己レビューした場合は公開前チェックとしては有効だが、「相互レビュー済み」とは扱わない

`.claude/rules/cross-agent-review.md` にこの役割分担表をルールとして固定しています。固定した理由は、セッションごとに「今回はどっちが書く番だっけ」を確認するコストを消したかったからです。役割が決まっていれば、書き始める前に「これは別 AI に通すための叩き台」と認識した状態で出力できます。

公開前に揃えるゲートも 4 条件で固定しました。

1. 作成者側のセルフチェックまたは `/article-review` 相当が済んでいる
2. もう一方の AI によるレビュー依頼またはレビュー結果が記録されている
3. 重大指摘が残っていない
4. ユーザーが公開を明示している

`published: true` への変更はこの 4 条件が揃うまで禁止する、と運用ルールで縛っています。AI 側に「公開してよい」と判断させないことが要点です。

## handoff ファイルにレビュー結果を必ず残すゲート

口頭やセッション内のやり取りでレビューを完結させると、後日「これいつ通したっけ」「何が指摘で何が任意改善だったか」が追えなくなります。`CLAUDE_CODE_HANDOFF.md` という単一の handoff ファイルに、作成・依頼・結果を時系列で積む方式に固めました。

1 件分の構造はこの形です。

```markdown
## 20XX-XX-XX 追記（X による <記事スラッグ> 初稿・Y レビュー依頼）

- 対象記事: `articles/<slug>.md`
- 状態: `published: false`
- 作成者: X
- 主題: <一文要約>
- レビュー担当: Y
- 触ってよい範囲: 原則 対象記事のみ
- `published: true` はユーザーが明示するまで変更しないこと

レビュー観点:
- <観点1>
- <観点2>
...

執筆時の一次情報補強:
- <gh api / コマンド / 確認できた事実>
```

レビュアーは結果を同じファイルの直下に追記します。

```markdown
Codex レビュー結果（20XX-XX-XX）:
- 公開可否: 🔴 修正必須 / 🟢 公開可
- 重大指摘1: <内容と該当行>
- 重大指摘2: <内容と該当行>
- 軽微指摘: <内容>
- NG語・守秘義務: 機械スキャン上は問題なし
```

「触ってよい範囲: 原則 対象記事のみ」を明記しているのは、レビュアーが指摘ついでに他ファイルまで直してしまう事故を防ぐためです。レビューと修正の権限を分けないと、誰が何を変えたかが追えなくなります。

handoff に積む副作用として、後日記事を書くときの素材が手元に増えます。本記事の実例セクションも、過去の handoff から指摘パターンを抜き出して構成しています。

## 実際に拾われた指摘パターン

ハーネス化してから引っかかった指摘を 4 種に分類します。

分類基準は、指摘が防いだ失敗の種類です。本文の主張が間違うものを「事実誤認」、公開してはいけない固有情報が残るものを「守秘リスク」、読者への見え方を損なう定型表現を「AI 的締め文」、Zenn 上での読みやすさや検索性を落とすものを「検索性とコードブロックの体裁」として分けました。

### 1. 事実誤認

- 「Aには X しかない」と書いたが、現在の既定ブランチでは X' も並存していた
- 参考リンクの既定ブランチ違いで 404
- ライブラリのバージョン記述が実コード (`package.json`) と食い違っていた

書いた AI は「自然な前提」として通しますが、別 AI が `gh api` や `cat package.json` で機械的に確認すると引っかかります。

### 2. 守秘リスク

- 業務ドメイン固有の Enum 名（`DomainSpecificTraining`、`ApplicationProcess` 相当）が透けて見える
- `isOnsite` のような実運用の語彙に近い変数名
- 「ある業務システムで」と一般化したつもりが、コード断片で具体が見える

これは作成側 AI が「サンプルとして自然」と通すパターン。別 AI に通すと「業務固有の語彙に見える」と検出できます。

### 3. AI 的締め文

AI 固有というより、こたつ記事的な紋切型表現を AI が再生してしまうパターンです。

- 「クォータ削減のヒントになれば。」
- 「参考にしてみてください」系の締め
- 「いかがでした...」系の問いかけ

書いた AI は「読者に語りかける自然な締め」と判定しますが、別 AI に通すと AI 的紋切型として弾かれます。記事末尾は特にこのパターンが出やすい箇所です。

### 4. 検索性とコードブロックの体裁

- タイトルに技術スタック名（`ASP.NET Core MVC` 等）が入っておらず検索性が低い
- コードブロックに Zenn の `言語:ファイル名` 指定（例: `csharp:Xxx.cs`）が付いていない
- `:::message alert` の使いどころが多すぎる、または足りない

これは「公開してから読みにくさで気づく」タイプの指摘です。別 AI のレビューを公開前に挟むと、タイトル設計・コードブロックのファイル名付与・強調の量を整える機会が増えます。

## ハーネス化前に踏んだ失敗

クロスレビュー運用に固める前、こんな落とし穴を踏みました。

**口頭で済ませて記録が残らない**：同じセッション内でレビューを終わらせ、修正もそのまま反映してしまい、何が指摘で何が任意改善だったかが後で追えなくなりました。handoff ファイルに残す形に変えたのはこれが直接の理由です。

**レビュアーが対象外まで直す**：「指摘ついでに、こっちの記事もちょっと整えておきます」を許してしまい、別記事の体裁が知らない間に変わっていたことがあります。`触ってよい範囲: 原則 対象記事のみ` を handoff に明記してから止まりました。

**同じ AI に自己レビューさせて満足する**：「Claude Code が Claude Code の出力をレビュー」「Codex が Codex の出力をレビュー」を相互レビュー扱いにしていた時期があります。これは公開前チェックには有効でも、別 AI による検出能力は得られません。役割固定をルール化してから、1 台で書いたら気づけなかった指摘が安定して引っかかるようになりました。

## まとめ

要点は3つです。

- 1 台の AI で書いて自己レビューする運用には、構造的に検出できない盲点（事実誤認・締め文紋切型・ドメイン語彙の漏れ）がある
- 作成者と別の AI を**役割固定**でレビュアーにし、結果を handoff ファイルに残すゲートに乗せる
- 公開判定の権限は AI に渡さず、4 条件（セルフ・相互レビュー記録・重大指摘なし・ユーザー明示）を人間が握る

個人記事を 2 台クロスレビューに乗せる価値は、品質よりも**自分の盲点が言語化されて残る**点にあります。handoff に積まれた指摘ログは、次の記事を書くときの観点リストとしてそのまま使えます。
