## はじめに

Claude Code を使い始めた直後は、ひとつの `CLAUDE.md` に「やってほしいこと」を全部書けば十分だと思っていました。

ただ、個人開発で何度も使っているうちに、だんだん別の問題が出てきました。ルールが長くなりすぎる。毎回同じ説明をしている。レビュー時に見る観点がぶれる。トークンが足りなくなるころには、最初に伝えた前提が薄くなっている。

この記事では、Claude Code を数ヶ月使う中で、運用をどう変えたかをまとめます。入門記事ではなく、自分の環境で実際に「入れたもの」と「捨てたもの」の記録です。

対象読者は、Claude Code や Codex のような AI コーディングエージェントを使い始めたものの、プロンプト・ルール・レビュー手順がまだ固まっていない個人開発者です。

実例として、Zenn記事管理リポジトリ [harness17/zenn-articles](https://github.com/harness17/zenn-articles) で使っているルール構成も出します。

## 最初はCLAUDE.mdに全部書いていた

導入直後は、グローバルな `CLAUDE.md` に運用ルールを直接書いていました。

最初のうちはこれで動きます。作業方針、禁止事項、よく使うコマンド、レビュー観点をまとめておけば、毎回ゼロから説明しなくて済むからです。

ただ、プロジェクトが増えるとすぐに苦しくなりました。

- Git操作のルール
- テスト方針
- セキュリティ観点
- APIクォータ設計
- データ設計レビュー
- ブラウザ検証
- 記事執筆ルール

これらを1ファイルに並べると、読ませたい内容と、そのタスクでは関係ない内容が混ざります。後から見返す自分にとっても、どこを直せばよいのか分かりにくくなりました。

そこで、グローバル側の `CLAUDE.md` は目次に寄せました。

```markdown
# グローバルルール
ユーザに同調せず、目的達成を優先する。

@rules/git-ops.md
@rules/api-quota-design.md
@rules/security-coding.md
@rules/data-design-review.md
@rules/test-strategy.md
@rules/perf-review.md

コード開発時に複数ファイルを生成、変更する規模の場合は変更内容を簡潔に説明後許可確認をすること
```

ここでやったことは単純です。ルールの本体を `rules/` 配下へ分け、`CLAUDE.md` は入口にしました。

この形にしてから、「テスト方針だけ直す」「APIクォータ設計だけ追加する」という変更がしやすくなりました。巨大なプロンプトを育てるのではなく、作業領域ごとの小さなルールを育てる感覚に近くなりました。

## プロジェクト固有ルールは別にした

グローバルルールだけでは、プロジェクト固有の文脈を持てません。

たとえば、このZenn記事リポジトリでは、通常のコード開発とは別の制約があります。

- `articles/*.md` のフロントマターは `published: false` で作る
- 公開前に文体・守秘義務・必須要素を確認する
- Codex が記事を書いたら ClaudeCode にレビュー依頼を残す
- ClaudeCode が記事を書いたら Codex にレビュー依頼を残す
- ユーザーが明示するまで `published: true` にしない

これはグローバルルールに入れるより、リポジトリ側に置いた方が自然でした。

実際にこのリポジトリでは、`AGENTS.md` と `.claude/rules/` に記事用のルールを分けています。

```text
.claude/rules/
├── article-requirements.md
├── cross-agent-review.md
├── privacy.md
├── topic-policy.md
├── writing-process.md
├── writing-style.md
└── zenn-workflow.md
```

ここで大事だったのは、「AIに何でも任せる」ではなく、「任せてよい範囲と止める条件」を先に書いたことです。

特に `published: true` は、AIエージェントが自分の判断だけで変えないようにしました。記事の公開は技術的には1行の変更ですが、公開後はZennに反映されます。だから、レビュー記録とユーザーの明示を公開ゲートにしました。

## skill化したのは定型作業を短くするため

次に変えたのは、繰り返す作業を skill に分けたことです。

記事執筆では、毎回だいたい同じ流れを踏みます。

1. テーマを決める
2. 想定読者を書く
3. 見出しを作る
4. コード例の候補を整理する
5. 記事を書く
6. 公開前レビューをする

これを毎回チャットで説明していると、会話の前半が手順説明で埋まります。そこで、このリポジトリでは `article-plan` と `article-review` を skill として分けました。

`article-review` では、チェック項目を表にしています。

```markdown
### 1. フロントマター

| 項目 | 必須/推奨 | チェック内容 |
|------|---------|------------|
| title | 必須 | 30〜40字、検索キーワード含む |
| emoji | 必須 | 設定済みか |
| type | 必須 | `tech` または `idea` |
| topics | 必須 | 1〜5個、英小文字 |
| published | 必須 | 公開直前のみ `true` |
```

skill にしたことで、依頼するときの言葉が短くなりました。

「候補Nの記事を書こう」と言えば、テーマ選定方針、記事要件、文体ルール、公開ゲートを読みながら進められる。毎回「Zennの記事なので、GitHubリンクを入れて、5行以上のコードを入れて、公開はfalseで」と説明しなくてよくなりました。

これはトークン節約だけではありません。定型作業をskillに寄せると、レビュー観点のぶれも減ります。

## CodexとClaudeCodeの役割を分けた

途中から、Claude Code だけで全部やるのではなく、Codex も併用するようになりました。

使い分けは、ざっくり次の形です。

| 役割 | 向いていた作業 |
|------|----------------|
| Codex | 実装、ファイル編集、テスト、記事本文の初稿 |
| ClaudeCode | 方針整理、レビュー、候補出し、別視点での確認 |

この分け方にした理由は、作業の性質が違ったからです。

コードや記事を実際に編集する作業では、ファイルを読んで、差分を作って、検証する流れが必要です。一方で、公開前レビューやテーマ選定では、少し距離を置いて「この切り口でよいか」「宣伝寄りになっていないか」を見る必要があります。

そこで、Zenn記事では相互レビューをルール化しました。

```markdown
| 作成者 | レビュー担当 | やること |
| --- | --- | --- |
| Codex | ClaudeCode | `CLAUDE_CODE_HANDOFF.md` と Skill Graph handoff にレビュー依頼を残す |
| ClaudeCode | Codex | `CLAUDE_CODE_HANDOFF.md` と Skill Graph handoff に Codex レビュー依頼を残す |
| ユーザー手動作成 | 直近で編集していない側を優先 | どちらがレビュー済みかを明記する |
```

最初は「AI同士にレビューさせるのは大げさでは」と思っていました。実際にやってみると、記事では効果がありました。

たとえば、個人開発アプリの具体例を書いていると、ドメイン固有の単語がそのまま出ることがあります。自分では自然に見えても、公開記事としては一般化した方がよい。別エージェントのレビューを挟むと、こういう漏れを拾いやすくなりました。

## ハンドオフを残すようにした

複数エージェントを使うと、次の問題は「どこまで終わったか」が分かりにくくなることです。

記事を書いた。レビューした。修正した。公開はまだ。次はユーザーの明示待ち。

この状態をチャットの中だけに置くと、次のセッションで忘れます。そこで、`CLAUDE_CODE_HANDOFF.md` と My-Skill-Graph の handoff に残すようにしました。

Zenn記事では、次のような内容を残します。

- 対象記事
- 作成者
- レビュー結果
- 修正した点
- 公開ゲートの状態
- 次にやること

特に効いたのは、公開ゲートの状態を表にしたことです。

```markdown
| 記事 | セルフチェック | 相互レビュー記録 | 重大指摘 | ユーザー指示 |
|------|----------------|------------------|----------|--------------|
| youtube-data-api-rss-quota-reduction | 済 | 済 | 残なし | 未指示 |
```

この表があると、次に開いた人間もAIも「今やってよいこと」が分かります。

公開してよいかどうかは、気分で判断するものではなくなりました。条件が揃っているかを見るだけになります。

## 捨てたものもある

運用を足していくと、ルールはすぐ増えます。増えたルールは、便利なようで、次の負担にもなります。

途中でやめたものもあります。

ひとつは、長いループ作業を会話内で全部抱え込むことです。作業を細かく分けずに「完成まで続けて」と依頼すると、途中で文脈が膨らみ、判断も雑になります。今は、構成、初稿、レビュー、公開のように段階を分けています。

もうひとつは、毎回アドバイザーを呼ぶことです。難しい設計判断では別視点が効きますが、通常の編集や明らかな修正まで相談すると遅くなります。そこで、アドバイザーを呼ぶ条件を「アーキテクチャ判断」「セキュリティ判断」「根本原因が難しいバグ」などに絞りました。

```markdown
## Opus に相談するタイミング

| 状況 | 例 |
|------|-----|
| アーキテクチャ判断 | 共通ライブラリに入れるべきか、呼び出し側に書くべきか |
| 複数の実装方針のトレードオフ比較 | リポジトリパターン vs 直接 DB アクセス |
| セキュリティ上の判断 | 認可ロジックの設計、CSRF 対策の範囲 |
```

AIエージェントの運用は、ルールを増やせば安定するわけではありませんでした。よく使うものはskillへ、判断が必要なものはルールへ、不要になった手順は消す。この整理を続ける方が効きました。

## 知識を会話の外に出すようにした

最後に大きかったのは、設計判断を会話の外へ出すことです。

その場のチャットで「AではなくBにした」と決めても、数週間後には理由が薄れます。後から記事にするにも、職務経歴書に転用するにも、「なぜそうしたか」が残っていないと弱い。

そこで、設計判断や戦略メモは My-Skill-Graph に残すようにしました。

```markdown
---
description: "判断の要旨を1文で"
alternatives: "検討した代替案"
rationale: "この選択をした理由"
project: "[[DevNext-index]]"
status: active
type: decision
created: YYYY-MM-DD
---

# <命題文>

## 判断の内容
## 検討した代替案
## この選択の根拠
## 注意点・トレードオフ
```

これは記事執筆にも効きました。

Zennの記事候補を考えるとき、ゼロからテーマを探すのではなく、過去の判断記録やhandoffから「詰まったこと」「比較したこと」「検証したこと」がある題材を拾えます。

今回の記事自体も、その流れで出てきた候補です。Claude Codeの機能紹介ではなく、「運用を変えた履歴」を記事にできるのは、途中の判断が残っていたからです。

## まとめ

数ヶ月使ってみて、Claude Code 運用で効いたのは、プロンプトを長くすることではありませんでした。

- グローバルルールは目次にして、詳細は `rules/` に分ける
- プロジェクト固有の制約はリポジトリ側に置く
- 繰り返す手順は skill にする
- Codex と ClaudeCode は作成者とレビュアーで分ける
- 公開や削除のような強い操作にはゲートを置く
- 設計判断は会話の外に残す

最初からこの形だったわけではありません。長すぎるルール、消えた文脈、レビュー漏れ、トークン枯渇を踏んで、少しずつこうなりました。

AIエージェントを開発や執筆に入れるなら、うまいプロンプトを1本作るより、運用を小さく分けて直せる形にしておく方が続けやすい。今はそう考えています。
