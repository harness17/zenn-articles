## はじめに

[前回の記事](https://zenn.dev/harness/articles/claude-code-harness-layer-map)でハーネスの全体像を5層の地図にし、[別の記事](https://zenn.dev/harness/articles/claude-code-harness-build-order)でゼロからどの順で組むかを書きました。今回は「なぜこの形にしたか」の話です。

ハーネスとは、Claude Code / Codex の運用を支える指示・設定・分担の総体です。rules、skills、hooks、agent分担、記録層で構成されています。

数ヶ月の運用で残った設計原則は3つです。**編集半径を小さくする**こと、**発火条件で層を分ける**こと、**捨てられる単位で持つ**こと。この3つがなぜ効くのかを、失敗した経験と一緒に書きます。

対象読者は、Claude Code や Codex のハーネスを組み始めたが、ファイル分割の粒度や構造の決め方に迷っている個人開発者です。

## 編集半径を小さくする

最初は `CLAUDE.md` 1枚に全ルールを書いていました。Git 操作、テスト方針、セキュリティ観点、API クォータ設計、記事の書き方が1ファイルに混ざっている状態です。

問題が起きたのは、ある日テスト方針の文言を直したときでした。テスト節の変更なのに、隣のセキュリティ節でインデントが崩れ、エージェントがセキュリティルールを読み飛ばしました。1行の修正が、関係ないルールの適用に影響した。

ここで `rules/` に分割して、`CLAUDE.md` を目次にしました。

```markdown
# グローバルルール
ユーザに同調せず、目的達成を優先する。

@rules/git-ops.md
@rules/test-strategy.md
@rules/security-coding.md
```

分割後は、`test-strategy.md` だけ開いて直せます。`security-coding.md` は触らない。編集半径が1ファイルに収まるので、修正が他のルールに波及しなくなりました。

逆に、分割しすぎると今度は「どのファイルに何があるか」を探すコストが増えます。私の場合はグローバルで18本、プロジェクト固有で8本あたりが上限でした。それ以上は目次を見ても把握しきれません。1ファイルが1つのトピック（Git操作、テスト方針、セキュリティ、等）に対応するくらいの粒度が、探しやすさと編集半径のバランスが取れました。

## 発火条件で層を分ける

ルールを分割した次に起きた問題は、「全部をルール（rules）に書いてしまう」ことでした。

たとえば、記事の公開前チェック（文体NG語スキャン、必須要素確認、守秘チェック）を最初はルールに書いていました。ルールは常時適用なので、記事を書いていないタスクでもチェック手順が読み込まれます。コード実装のセッションで記事レビュー手順が混ざると、エージェントの注意が散ります。

これをスキル（skill）に移したら、呼んだときだけ走るようになりました。一方、記事保存時の文体チェックはフック（hook）にしました。保存のたびに自動で走り、呼び忘れがありません。

| 種類 | 発火条件 | 使いどころ |
|------|----------|-----------|
| rules | 常時適用（黙って効く） | 毎タスクで守るべき制約（Git操作、セキュリティ） |
| skills | 明示的に呼び出す | 定型作業（レビュー、リリース前チェック） |
| hooks | ツール実行時に自動 | 保存時の文体チェック、コミット前の警告 |
| advisor | 難所だけ相談 | アーキテクチャ・セキュリティ判断 |

この4種を混ぜて1箇所に置くと、常時走るべきものが呼び忘れで抜けたり、呼んだときだけ走ればいいものが毎回発火してノイズになったりします。発火条件が違うものは、層として分けた方が管理しやすくなりました。

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          { "type": "command", "command": "bash .claude/hooks/check-article-style.sh 2>/dev/null || true", "timeout": 10 }
        ]
      }
    ]
  }
}
```

hookは保存時に自動で走り、ルールやスキルとは別の制御です。この分離がないと、「呼んだか呼ばなかったか」の曖昧さが残ります。

## 捨てられる単位で持つ

ハーネスの部品は足すだけでなく、外すこともあります。使っていないルールをそのまま残すと、エージェントがコンテキストに読み込む量が増えて判断が鈍ります。

ここで大事だったのは、**1つのルールを外したとき、他のルールが壊れないこと**です。たとえば `perf-review.md`（パフォーマンスレビュー）を外しても、`test-strategy.md` や `security-coding.md` は独立して動きます。各ルールが他のルールに依存していなければ、不要になったものを安全に削除できます。

実際に、リリース前チェックのスキルが「`sprint-contract.md` の完成条件リストを参照して検証する」と書いてあった時期がありました。`sprint-contract.md` の書き方を変えたら、リリース前チェックも壊れた。ルール間で実行順序や参照を作ると、片方を外したときにもう片方が壊れます。私の場合、ルール間の参照は「関連として存在を知っている」程度にとどめ、実行順序の依存は作らないようにしました。

間引く判断の合図は、③の記事にも書きましたが、**ルールを読んでも作業の質が変わらなくなったとき**です。毎回読み込まれているのに効果が出ていないルールは、残す根拠がありません。

## 判断の根拠を会話の外に残す

ルールを足したり削ったりするうちに、「なぜこのルールを入れたのか」が分からなくなりました。チャットの中で「AではなくBにした」と決めても、数週間後にはセッションが終わっていて理由を辿れません。

結果として、同じ趣旨のルールを二重に作ったことがあります。既存のルールに気づかず、少し違う言い回しで同じ制約を追加していました。

そこで設計判断は命題文をタイトルにしたノートに、次セッションへの引き継ぎは handoff に残すようにしました。ルールの「何」はファイルに書いてあるけれど、「なぜ」は別の記録として持たないと、後で足し引きの判断ができなくなります。

これは①の記事で書いた第5層（記録層）の話です。ルール本体とルールの根拠を分けて持つことで、「このルールはもう要らない」「このルールはまだ必要」の判断に使えます。

## まとめ

ハーネスを「小さく分けて直せる形」にした理由は3つです。

- **編集半径を小さくする**: 1ファイルの修正が他のルールに波及しない。18本前後が粒度の目安
- **発火条件で層を分ける**: 常時（rules）/ 明示（skills）/ 自動（hooks）/ 難所（advisor）を混ぜない
- **捨てられる単位で持つ**: ルール間の順序依存を作らず、不要になったら安全に外せるようにする

これらは「こうすべき」という設計論ではなく、「こうしなかったら困った」という体験から出た判断です。組み上がった全体像は [5層の地図](https://zenn.dev/harness/articles/claude-code-harness-layer-map)、ゼロからの組み方は [ビルド順](https://zenn.dev/harness/articles/claude-code-harness-build-order) を参照してください。
