## はじめに

前回、[Claude Code運用ハーネスの現在地](https://zenn.dev/harness/articles/claude-code-harness-layer-map) で、今のハーネスを「入口 → 制約 → 定型作業 → 実行 → 記録」の5層に整理した地図を書きました。あの記事は「今どうなっているか」の地図です。

ただ、あの全体像を見て「最初からこれを全部組もう」とすると、たぶん失敗します。実際、私自身が早い段階で `rules/` 分割や skill 量産に手を出して、使う前に仕組みの保守で疲れたことがありました。

この記事は、ハーネスを**ゼロからどの順で組むか**の手順です。ポイントは2つあります。最初から全部やらないこと。そして、各段階に「次へ進む合図」を置いて、痛みが出てから1段ずつ足すことです。

対象読者は、Claude Code を導入したものの運用が固まらず、何から手をつけて何を後回しにすべきか迷っている個人開発者です。「ハーネス」はエージェントの運用を支える指示・設定・分担の総体を指します。なお、入門記事ではないので「skill とは何か」のような説明はしません。あくまで導入順序の判断に絞ります。

各ステップは「何を入れるか / なぜこの順か / 早すぎる（または入れない）と何が起きるか」で書きます。先に全体の合図を一覧にしておきます。

| Step | 入れるもの | 次へ進む合図 |
|------|-----------|-------------|
| 0 | 素の `CLAUDE.md` 1枚 | （最初から分割しない） |
| 1 | 目次化（`@` で別ファイル読み込み） | 関係ない節を毎回読み飛ばし始めたら |
| 2 | skill を1つだけ | 同じ手順説明を3回したら |
| 3 | 強い操作にゲート | 取り消しにくい操作が手順に出てきたら |
| 4 | Codex と役割分担 | 自分で書いて自分で見て、公開後に抜けに気づいたら |
| 5 | 記録層 | 先週なぜそうしたか思い出せなくなったら |
| 6 | 増やしすぎを間引く | ルールを読んでも作業の質が変わらなくなったら |

## Step0: まず素のCLAUDE.md 1枚で始める

最初は、分割もスキルもなしで構いません。`CLAUDE.md` 1枚に、方針と禁止事項を数行書くだけで動きます。

```markdown
# 方針
ユーザに同調せず、目的達成を優先する。

# 守ること
- コードを複数ファイル変更する規模なら、変更内容を説明してから許可を取る
- 公開・削除のような操作は勝手にやらない
```

ここで `rules/` 分割や skill 設計から始めると、早すぎる抽象化になります。まだ繰り返しの痛みが出ていない段階で構造を作ると、使われないまま保守対象だけが増える。最初の数日は、素の1枚で実際の作業を回すのが先です。

## Step1: 苦しくなったら目次化する

1ファイルにルールを足し続けると、いずれ読みにくくなります。Git のルール、テスト方針、セキュリティ観点、記事の書き方が1枚に混ざると、そのタスクに関係ない節まで毎回読むことになる。

**次へ進む合図は「関係ない節を毎回読み飛ばし始めたら」です。** このサインが出たら、本体を `rules/` に分けて、`CLAUDE.md` を目次にします。

```markdown
# グローバルルール
ユーザに同調せず、目的達成を優先する。

@rules/git-ops.md
@rules/test-strategy.md
@rules/security-coding.md
```

目次にしておくと、「テスト方針だけ直す」が巨大な1ファイルを触らずに済みます。分割はこの合図が出てからで十分間に合います。

## Step2: 繰り返す手順を1つだけskill化する

次は、繰り返す作業をスキルに切り出します。ここで全部をスキル化しないのが大事です。最も繰り返している1手順だけ切り出します。

**次へ進む合図は「同じ手順説明を3回したら」です。** 3回説明したなら、その手順は定型です。

スキルには起動条件と中身を書きます。たとえば記事の公開前チェックなら、こんな形です。

```markdown
## 起動条件
- 「記事をレビュー」「公開前チェック」と言われたとき
- published を true に変える前

## チェック項目
- フロントマター（title / topics / published）
- 文体NG語スキャン
- GitHub リンク・5行以上のコード・体験例
- 守秘義務（顧客名・本名）
```

早すぎると、使わないスキルが増えて、どれを呼ぶか自分で忘れます。1つ作って効果を感じてから、次の定型を足す方が続きます。

## Step3: 強い操作にゲートを置く

スキルで作業が速くなると、今度は「やり直せない操作」をエージェントが勝手に実行するリスクが出てきます。公開、削除、push などです。

**次へ進む合図は「取り消しにくい操作が手順に出てきたら」です。** その操作にだけ、明示確認のゲートを足します。

たとえば記事の公開（`published: true`）は、技術的には1行の変更ですが、公開後は外部に反映されます。だから、条件が揃うまで変えないようにしました。

| ゲート対象 | 通過条件 |
|-----------|----------|
| `published: true` への変更 | セルフチェック済み・相互レビュー記録あり・重大指摘なし・ユーザーの公開明示あり |

ゲートは全部の操作に付ける必要はありません。取り消しコストが高い操作に絞ります。

## Step4: 2台目を入れて役割分担する

1台のエージェントで実装もレビューもすると、自分の書いたものを自分で見ることになり、見落とします。

**次へ進む合図は「自分で書いて自分で見て、公開後に抜けに気づいたら」です。** ここで2台目（私の場合は Codex）を入れて、作成者とレビュアーを分けます。

| 役割 | 向いていた作業 |
|------|----------------|
| Codex | 実装・ファイル編集・初稿 |
| ClaudeCode | 方針整理・レビュー・別視点の確認 |

そのうえで、作成者とレビュアーが同じにならないよう、相互レビューをゲートにしました。早すぎると、作業量がないのに2台運用の調整コストだけ増えます。1台で見落としの痛みが出てからで十分です。

## Step5: 記録層を足す

複数セッション・複数エージェントになると、次の問題は「先週なぜそうしたか」が消えることです。チャットの中だけに判断を置くと、次に開いたときに理由を思い出せません。

**次へ進む合図は「先週なぜそうしたか思い出せなくなったら」です。** ここで、判断と引き継ぎを会話の外に出します。設計判断は、命題文をタイトルにしたノートで残しています。

```markdown
---
description: "判断の要旨を1文で"
alternatives: "検討した代替案"
rationale: "この選択をした理由"
status: active
type: decision
---

# <命題文>
```

これは設計判断を記録するための汎用的な仕組みで、ノートの中身そのものは公開しません。次セッションへの引き継ぎは別途 `handoff` に残します。後から記事にするときも、この記録があると「詰まったこと」「比較したこと」を題材に拾えます。

これも早すぎると、まだ誰も読み返さないノートの管理だけが増えます。判断を思い出せなくて困った経験が出てから足すくらいで間に合いました。

## Step6: 増やしすぎを間引く

最後に、足すだけでなく捨てる話です。ルールやスキルは足すほど安定する、とは限りませんでした。増えた手順は次の負担にもなります。

私がやめたものを2つ挙げます。ひとつは、長いループ作業を会話の中で全部抱え込むこと。途中で文脈が膨らみ、判断が雑になりました。今は構成・初稿・レビュー・公開と段階を分けています。

もうひとつは、毎回アドバイザー（上位モデル）に相談すること。難所では効きますが、明らかな修正まで相談すると遅くなる。今はアーキテクチャ判断やセキュリティ判断など、別視点が効く局面に絞りました。

足す合図と同じくらい、間引く判断も運用の一部です。

## まとめ

ハーネスをゼロから組むときに効いたのは、次の3つでした。

- 最初から全部やらない。素の `CLAUDE.md` 1枚から始める
- 各段階に「次へ進む合図」を置き、痛みが出てから1段ずつ足す
- 足すだけでなく、使っていないものを間引く

この記事は「どう組むか（HOW）」でした。次は「なぜ小さく分けて直せる形にするのか（WHY）」の設計思想を別記事にする予定です。組み上がった全体像は、前回の [5層の地図](https://zenn.dev/harness/articles/claude-code-harness-layer-map) を見てください。
