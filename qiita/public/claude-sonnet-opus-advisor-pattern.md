## 詰まったこと

Claude Code に実装を任せていて、ルーティンな CRUD やビュー生成は速いのに、**設計判断が要る場面で挙動が安定しない** 問題がありました。

- アーキテクチャの分岐（共通ライブラリに入れるか、呼び出し側に書くか）で、確認せず片方に突き進む
- 原因不明のバグで、仮説を立て直さずに同じ修正を繰り返す
- 「これで完成」と判断する基準が甘く、抜け漏れに気づかない

実装スピードを優先して安いモデルに寄せると難所で判断がぶれ、難所のために常に賢いモデルを使うと、ルーティン作業のコストまで上がる。このトレードオフをどう切るかで詰まりました。

## 結論: 実行役と助言役をモデルごと分ける

実装の実行は速いモデル（Sonnet）に全部任せ、**判断が難しい局面だけ** 賢いモデル（Opus）に助言を求める、という役割分担に落ち着きました。

| 役割 | モデル | 担当 |
| --- | --- | --- |
| Executor（実行役） | Sonnet | 実装・ファイル操作・ビルド・テスト |
| Advisor（助言役） | Opus | 方針・代替案・完成条件の妥当性確認だけ |

ポイントは、**助言役はツール実行も最終出力もしない** ことです。計画・方針・修正案を返すだけで、実行は必ず実行役に戻します。「Sonnet が走り、Opus が考える」という切り分けです。

## 実装: Agent ツールの model 指定で切り替える

Claude Code では、サブエージェント呼び出し（Agent ツール）の `model` を上書きすることで、同じセッション内で助言役だけ別モデルに切り替えられます。

```
Agent ツール:
  subagent_type: general-purpose
  model: "opus"
  prompt: |
    以下の判断について助言をください。実装はしなくてよい。
    方針・理由・代替案だけ返してください。

    状況: [現在の文脈]
    検討している選択肢:
    1. リポジトリパターンで共通層に寄せる
    2. 呼び出し側で直接 DB アクセスする
    判断したいこと: どちらが保守コスト的に妥当か
```

返ってきた方針を受けて、実装は実行役（Sonnet）が行います。助言役に「実装するな、方針だけ返せ」と明示するのが効きました。これを書かないと、助言役がそのままコードを書き始めて役割分担が崩れます。

## 助言を求める場面・求めない場面

毎回 Opus に投げると役割分担の意味がなくなるので、呼ぶ条件を決めました。

**助言を求める:**

- アーキテクチャ判断（どの層に置くか）
- 複数の実装方針のトレードオフ比較
- 認可・CSRF などセキュリティ設計の判断
- 根本原因が特定できない複雑なバグ
- 「完成」と判断してよいかの第三者確認

**助言を求めない:**

- ルーティンな実装（CRUD・ビュー生成・DI 登録）
- スタックトレースが明確なビルドエラー修正
- ファイルの読み書き・検索
- コミット・ブランチ操作

## 助言を鵜呑みにしない

運用してみて重要だったのは、**助言を絶対視しない** ことでした。助言どおりにやって実際に失敗したり、一次情報（ドキュメントや実コード）が助言と矛盾したりしたら、実行役側の観測を優先します。

逆に、自分が集めたデータと助言が食い違うときは黙って切り替えず、「自分はこういう根拠で X を見つけた、あなたは Y を勧める、どちらの制約が優先か」ともう一度助言役に投げ直す。これで「賢いモデルの言うことを盲従して間違える」事故を減らせました。

## まとめ

- 1 つのモデルに実装も判断も全部やらせると、難所で判断がぶれるかコストがかさむ
- 実行役（Sonnet）と助言役（Opus）を分け、助言役は方針だけ返して実行はしない、という切り分けにした
- Agent ツールの `model` 指定で、難所だけ助言役に切り替える
- 助言は鵜呑みにせず、実コード・ドキュメントの一次情報や実測と矛盾したら実行役の観測を優先する

この運用ルールは個人開発のハーネス（[zenn-articles リポジトリ](https://github.com/harness17/zenn-articles) ほか）の `rules/` に記録して、毎セッション読ませています。
