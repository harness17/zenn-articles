# qiita-article-review

`qiita/public/<slug>.md` を公開前に検査する。レビューだけの依頼では指摘を表形式で出し、修正は自動でしない。ユーザーが「レビュー対応」「コメント対応」「直して」と明示した場合は、対象コメントを分類して最小修正する。

## 起動条件

- ユーザーが「Qiita記事をレビュー」「Qiita公開前チェック」「推敲」と言ったとき
- ユーザーが「レビュー対応」「コメント対応」「指摘を直して」と言ったとき
- フロントマターを `ignorePublish: false` または `private: false` に変更しようとしているとき
- `/qiita-article-review` で呼ばれたとき

## チェック項目

### 1. フロントマター

| 項目 | 必須/推奨 | チェック内容 |
|------|---------|------------|
| title | 必須 | 検索キーワードを含む、30〜45字目安 |
| tags | 必須 | **1〜5個（Qiita仕様の上限）**、慣例で大文字混在可（例: `Node.js`, `YouTubeAPI`） |
| private | 必須 | 公開時 `false`、限定共有時 `true` |
| ignorePublish | 必須 | 編集中 `true`、公開直前のみ `false` |
| id | 自動 | 初回公開時に Qiita CLI が付与する。手動編集しない |
| updated_at | 自動 | Qiita CLI が更新する。手動編集しない |

### 2. 文体ルール違反語スキャン

以下の語を grep し、ヒットしたら行番号と該当箇所を表示：

```
NG語リスト（@.claude/rules/writing-style.md と同期）:
- 素晴らしい / 驚くべき / 画期的 / 魔法のように
- いかがでしたでしょうか / いかがだったでしょうか
- ぜひ参考にしてみてください / ご参考になれば幸いです
- 〜とされている / 〜と言われている（一次情報なら断言する）
- 皆さんも試してみてください
```

`〜ing 連鎖`（同じ段落内で「〜することで」が3回以上）も検出する。

### 3. 必須要素チェック（Qiita版）

| 要素 | 検出方法 |
|------|---------|
| 結論コード（TL;DR）の先出し | 冒頭500字以内にコードブロックがあるか |
| 再現条件 | 環境・バージョン・最小再現コードが明示されているか |
| 原因の一次情報リンク | 仕様書・MDN・公式ドキュメントのURLが含まれるか |
| 実コード（5行以上） | コードブロックの最大行数を計測 |
| 文字数 | 1200〜3000字（Qiitaは短くても可、長すぎは避ける） |

### 4. 守秘義務チェック

以下のキーワードに該当する固有名詞が含まれていないか：

- 過去勤務先名（トランスワード、プロアクティブ）
- 顧客名（ボートレース下関、旅行業の固有社名 等）
- 同僚・関係者の実名
- ローカルパス（`C:\Users\<user>` など）
- 個人情報を含む handoff / goals の生引用

該当があったら必ず指摘する。一般化を提案する。

### 5. 構成チェック（Qiita版）

- 「TL;DR / 結論コード」が冒頭にあるか（Qiitaは検索流入が中心、結論先出しが効く）
- 「再現条件」「原因」「解決」のセクションが明確に分離されているか
- 「1記事1トラブル」の方針から外れて、複数トピックが混ざっていないか
- 見出しが3〜5個か（Qiitaは長すぎると離脱しやすい）
- コードブロックに言語指定があるか（` ``` ` だけのブロックは検出）
- JavaScript のコードブロックは `javascript` より `js` を優先
- URL だけのコードブロックは `text` のまま放置せず、直前に説明を置く
- 参考リンクには、リンク先が何を補うものか短い説明があるか
- 元となる Zenn 記事がある場合、冒頭に **「Zenn記事から〇〇に絞った再構成」** と明示しているか
- 非公開または未公開のリポジトリを根拠にする場合、読者がリンク先で検証できない前提を本文に明記し、必要な抜粋コードだけで1トラブルの原因と修正が追えるか
- セキュリティリスクやエラー内容を説明するとき、実際に起き得る情報（内部URL、リクエスト詳細、ファイルパス等）に寄せており、APIキーや個人情報など未確認の漏洩を過大に断言していないか

### 6. 明確性重点チェック

Lapras の明確性コメントを優先して確認する。Qiita は短くても、検索で来た読者が「なぜこの1点が問題になるか」を理解できる必要がある。

- 冒頭で「何が起きたか」だけでなく「放置すると何に困るか」が説明されているか
- 対象読者の環境・前提・バージョンが分かるか
- 初心者が誤解しやすい仕様、用語、API挙動が1文で補足されているか
- 採用した解決策だけでなく、捨てた解決策と理由が最低1つあるか
- 解決後に確認したコマンド、画面、ログ、DOM状態などが具体的か
- 元Zenn記事がある場合、この記事では何を捨てて何に絞ったかが明示されているか

### 7. Qiita記法チェック

- 重要な注意点・落とし穴は通常の箇条書きだけで流さず、必要に応じて `:::note warn` または `:::note alert` で強調する（Zennの `:::message` ではない）
- 補足的な長い手順や背景説明は `:::note info` を検討する
- 折りたたみは `<details><summary>...</summary>...</details>`（HTMLタグ）が使える
- ただし Qiita 記法は強調したい箇所に限定し、1記事内で多用しすぎない

### 8. タグ規約チェック（Qiita固有）

- tags は最大5個。**6個以上は Qiita CLI でエラー**
- 各タグは1文字以上、空タグなし
- 検索されにくい独自タグ（`MyAppName` など）を避け、`Chrome` `JavaScript` `Electron` のような既存タグを優先
- 候補表記の慣例: `Node.js`, `YouTubeAPI`, `Chrome拡張`（公式タグ表記に合わせる）

### 9. 相互レビューゲート

- 作成者が Codex の場合、ClaudeCode へのレビュー依頼またはレビュー結果が `CLAUDE_CODE_HANDOFF.md` に残っているか
- 作成者が ClaudeCode の場合、Codex へのレビュー依頼またはレビュー結果が `CLAUDE_CODE_HANDOFF.md` に残っているか
- 継続作業に関わる場合、My-Skill-Graph の `ops/handoffs/` または `self/goals.md` に次アクションが残っているか
- `ignorePublish: false` への変更は、相互レビュー記録とユーザーの公開指示が揃うまで止める

### 10. 中心主張の事実整合チェック（@.claude/rules/article-fact-check.md と同期）

個人開発リポジトリの実コードに言及する記事は、以下を確認する：

- 「A には X しかない」「A は Y 非依存」「A→B で新規追加」のような断言を含む記事は、`gh api` でファイル全体・依存リスト・コミット履歴を確認したか
- 参考リンクの `blob/<branch>` 部分は、`gh api repos/<owner>/<repo> --jq '.default_branch'` で確認したブランチ名と一致するか
- csproj / package.json / requirements.txt の依存関係を確認したか

## レビューコメント対応モード

ユーザーがレビューコメントを貼って「対応して」と依頼した場合は、次の順で処理する。

1. コメントを分類する
   - 技術的誤り・リンク確認・記法修正: 原則対応する
   - 読者向け補足: 本文の流れを崩さない範囲で1〜2文だけ足す
   - 明確性・読みやすさ: 背景、放置した場合の困りごと、前提用語、捨てた解決策、確認方法を最小追記する
   - 講評・称賛・任意改善: 本文へ取り込まない
2. 外部ツールや現在性のある情報への指摘は一次情報で確認する
3. コード例への指摘は、読者がコピーしたときのコンパイル・実行単位を意識する
4. 修正後に必ず再チェックする
   - 文体NG語スキャン・守秘・事実整合を再チェックする（コメント対応で触れた範囲に絞る）
   - `git diff -- <対象記事>` で差分がコメント対応に収まっているか
5. Codex への相互レビュー依頼テンプレを自動追記する
   - リポジトリルートで `bash .claude/skills/article-review/scripts/append-codex-review-request.sh <記事ファイル名>` を実行
   - スクリプトは Zenn 用と共有。対象記事パスは Qiita 記事のパス（`qiita/public/<slug>.md`）を渡したい場合、引数を `qiita/public/<slug>.md` 相対パスにできるよう必要に応じてスクリプト側を拡張する。当面は記事名だけを渡し、テンプレ内の対象ファイル欄を `qiita/public/<slug>.md` に Edit で書き換える

## やらないこと

- 自動修正（ユーザーが判断する）
- 内容の意味的レビュー（事実誤認は別途、アドバイザーモデルで確認する）
- `npm run qiita:publish` の実行（publish スキルに任せる）

## 完了条件

- すべてのチェック項目について結果を報告した
- 公開可否判断（🟢 / 🟡 / 🔴）を提示した
- 相互レビュー記録の有無を報告した
- 明確性重点チェックについて、背景・前提・代替案・確認方法の不足有無を報告した
