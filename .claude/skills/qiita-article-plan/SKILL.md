# qiita-article-plan

新しい Qiita 技術記事の企画・構成を行う。出力は `drafts/qiita-<slug>.md` に保存し、執筆前段階の構成成果物を作る。

## 軸となる方針

**「1記事1トラブル」**（`drafts/qiita-article-candidates.md` と同期）。

- Zenn: 体験全体、設計判断、作ったものの背景、学び
- Qiita: **詰まった1点**、原因、再現条件、解決コード、注意点
- 既存 Zenn と同じ題材でも、Qiita では検索される具体トラブルへ切り出す
- 単なる網羅解説（「〇〇まとめ」「〇〇入門」）は書かない
- 実コードに触れる候補は、執筆前に該当リポジトリの事実確認を行う

このスキルは、ユーザー提案が「Zennの再投稿」や「網羅解説」に寄っているとき、**指摘して切り出し方を再考させる**。

## 起動条件

- ユーザーが「Qiita記事を企画」「Qiita向けに切り出す」「Qiitaの構成を考えて」と言ったとき
- 既存の `drafts/qiita-<slug>.md` を更新したいとき
- `/qiita-article-plan` をスラッシュコマンドで呼ばれたとき

## 実行ステップ

### 0. 候補と既存記事の照合

テーマを提案する前に `drafts/qiita-article-candidates.md` を確認する。

- `既存 Qiita 公開記事` と `レビュー待ち` を重複して提案しない
- 既存記事と近いテーマは、**Qiitaとしての差分**（どの1点に絞るか）が言える場合だけ候補に残す
- 新しい構成メモを作成または更新したら、対応候補の `次の扱い` 列を更新する
- 候補外の派生記事を作る場合も、`drafts/qiita-article-candidates.md` のどこかに slug と主題を追記する

### 1. テーマ確認（質問する）

候補表（最優先 / Chrome拡張系 / Electron系 / YouTube API系 / ASP.NET Core系 / AIエージェント系）を念頭に、ユーザーから次を引き出す：

- どの候補か（slug または自由記述）
- **詰まった具体的な1点は何か**（複数言ったら絞らせる）
- 再現コードまたは再現手順を示せるか
- 解決後の確認方法はあるか

「詰まった1点」が言語化できないなら、別候補に切り替える。

### 1.5. 方針チェック（必ず行う）

| OK パターン | NG パターン |
|------------|------------|
| 「YouTubeのSPA遷移後にcontent scriptが効かない → matchesで解決」 | 「Chrome拡張の作り方まとめ」 |
| 「Chart.jsの描画が終わる前にPDF化されて白紙になった → waitForFunctionで解決」 | 「Playwright入門」 |
| 「MutationObserverがDOM並び替えで再発火 → 差分更新で回避」 | 「DOM操作のベストプラクティス」 |

NG パターンは候補表の `次の扱い` 通りの具体トラブルに掘り下げる。掘り下げられないなら別候補へ。

### 2. 想定読者を1文で言語化

「〇〇を実装中に△△で詰まった人」のように検索される具体性で書く。曖昧な「Chrome拡張開発者」「Web開発者」は禁止。

### 2.5. 検索キーワードを先に決める

Qiita は検索流入が中心。構成段階で次を確定する。

- 詰まった人がGoogle / Qiita検索で叩くキーワード3〜5個（例: `content_scripts matches 効かない`, `YouTube SPA pushState 拡張`）
- 該当キーワードがタイトル・見出し・本文の冒頭に入るか

### 3. 見出し3〜5個を提案

Qiita向け推奨構成（4セクション固定が読みやすい）：

1. **TL;DR / 結論コード**（150〜250字、最初に解決コードを出す）
2. **何が起きたか / 再現条件**（環境・バージョン・最小再現コード）
3. **原因**（仕様や挙動の説明、一次情報リンクつき）
4. **解決と注意点**（採用コード、別解、ハマりやすい派生ケース）

任意でセクション5「補足・関連トラブル」を追加可。

各見出しで以下を箇条書き化：
- 何を伝えるか（1文）
- 具体例（コード or 出力 or DOM断片）
- 想定文字数

### 4. コード例の準備リスト

| セクション | コード言語 | 出典 | 準備状況 |
|----------|----------|------|---------|

- 出典が個人開発リポジトリの場合は、リポジトリ名と該当ファイルパスを書く
- 抜粋ではコンパイル/実行できなくなる例は、`import` や `using` を補ったか確認する

### 5. drafts/qiita-<slug>.md に書き出し

スラッグは英数小文字とハイフン。例：`youtube-spa-content-script-matches`, `playwright-wait-chartjs-before-pdf`。

ファイル構成：

```markdown
# <記事タイトル案>

## メタ情報
- tags候補: [tag1, tag2, ...]（5個以内、Qiita慣例で大文字混在可）
- 想定文字数: 1500〜2500字（Qiitaは短めでも成立）
- 想定執筆時間: 3〜5時間
- ステータス: 構成中 / 執筆中 / 推敲中
- 元になった体験: <Zenn記事 or リポジトリ or 実装中の出来事>

## 想定読者
（1文で。検索キーワードを含む）

## 検索キーワード候補
- ...

## 構成

### 1. TL;DR / 結論コード（150〜250字）
- 結論の1〜2文
- 解決コード（最小）

### 2. 何が起きたか / 再現条件
- 環境・バージョン
- 最小再現コード
- 期待動作と実際の動作

### 3. 原因
- 何が原因だったか
- 一次情報リンク（仕様書・MDN・公式ドキュメント）

### 4. 解決と注意点
- 採用した解決策
- 別解と捨てた理由
- ハマりやすい派生ケース

### 5. （任意）補足・関連トラブル

## コード例の準備状況
（表）

## 参考リンク候補
- 公式ドキュメント
- 関連リポジトリ（DevNext / youtube-schedule など）
- 元になった Zenn 記事（あれば）
```

## 守ること

- 文体ルール（@.claude/rules/writing-style.md）に違反しない見出し案を提案する
- 守秘義務（顧客名・案件名・同僚名）は構成メモにも書かない
- 個人開発リポジトリ（DevNext など）の言及方針は CLAUDE.local.md の表に従う
- **個人開発リポジトリの実コードに言及する記事は、構成案を出す前に @.claude/rules/article-fact-check.md のチェックリストを通す**
- Zenn 記事の再投稿になっていないか毎回確認する。同じ題材なら**何を捨てて何を残したか**を構成メモに明記する

## 完了条件

- `drafts/qiita-<slug>.md` が作成または更新された
- 対応候補の `次の扱い` が `drafts/qiita-article-candidates.md` で更新された
- ユーザーが構成案にOKを出した
- 次のアクション（執筆開始 or 構成練り直し）が明確になっている
