# 記事執筆時の事実確認ルール（reflection from M article incident）

## なぜこのルールがあるか

M 記事（候補M「DevNet/DevNext 差分」、現 `aspnet-core-identity-to-commonlibrary.md`）の執筆では、**記事の中心主張に関わる事実誤認を 3 回連続で踏みました**。

| 試行 | 中心主張 | 誤認内容 |
|------|---------|---------|
| 1回目 | 「BaseController 系の多重 Generic で読めなくなった」 | DevNet/DevNext どちらにも `BaseController` は存在しなかった |
| 2回目 | 「DevNet は2型版のみ → DevNext で3型版を並列追加」 | DevNet master にも3型版が初期コミットから並存していた（`head -60` で見ていて見落とした） |
| 3回目 | 「DevNet の `CommonLibrary` は Identity 非依存だった」 | DevNet `CommonLibrary.csproj` は `Microsoft.AspNet.Identity.*` 4 種を参照し、`EntityBase.GetUserId()` で Identity 関数を呼んでいた |

毎回 Codex の相互レビューで指摘され、軸を組み立て直しました。執筆と確認のコストが想定の 3 倍以上膨らみました。

## 守ること

### 1. 中心主張になる事実は、ファイル全体を確認してから書く

抜粋ツールで一部だけ見て「ない」と判断しない。

- ❌ `head -60` だけで「DevNet には3型版がない」と結論
- ✅ ファイル全体のクラス宣言を `grep -n "abstract class\|where T"` で列挙してから判断
- ✅ 大きいファイルは `gh api repos/owner/repo/git/trees/<ref>?recursive=1` でツリー全体を取ってから

### 2. csproj / package.json / requirements.txt も依存の事実として確認する

「コードに `using X` がない = X 非依存」とは限らない。プロジェクトファイルの参照を必ず見る。

- ✅ `.csproj` の `<PackageReference>` / `<Reference>` 一覧
- ✅ `package.json` の `dependencies` バージョン
- ✅ ライブラリの破壊的変更（CJS→ESM 等）が記事中心主張なら、移行ガイドや CHANGELOG も確認

### 3. テーマ確定前に「中心主張の反証」を 1 回試みる

主張を書く前に、その主張を否定する証拠が存在しないか **1 回だけ探す**。

- 主張: 「A には X しかない」→ 反証クエリ: A の全範囲で X 以外の派生がないか
- 主張: 「A は Y 非依存だった」→ 反証クエリ: A の依存リストに Y 関連が含まれていないか
- 主張: 「A→B で新規追加した」→ 反証クエリ: A の最古コミットで既に存在していないか

反証クエリで何も出なければ主張に進む。出たら軸を見直す。

### 4. 既定ブランチは必ず確認する

`blob/main` 形式を雑に書かない。

- ✅ `gh api repos/owner/repo --jq '.default_branch'` で確認
- ✅ 参考リンクは確認したブランチ名で生成
- ✅ コミット履歴に依存する主張は、コミット固定 URL (`blob/<sha>`) で書く

### 5. ユーザーへの軸絞り込み質問は、軸自体の事実裏取りを質問前にする

「Generic を入れすぎた失敗の具体例はどれですか？」のように選択肢を出す前に、各選択肢が**実コードに存在するか**を確認してから出題する。

- ❌ ユーザーに「BaseController 系の多重 Generic」を選ばせた → 実は BaseController が存在しなかった
- ✅ 質問前に `gh api` で実体を確認し、存在する選択肢だけを提示する

## 適用タイミング

- 個人開発リポジトリの実コードを引用する記事（DevNet/DevNext/youtube-schedule/google-chrome-extensions/Phycock 等）
- 「A は X だった」「A→B で変わった」など、リポジトリの状態を断言する記事
- 二世代以上のテンプレートや、ライブラリのバージョン跨ぎを扱う記事

これらは **公開後に発覚した事実誤認の修正コストが、執筆中に確認するコストの 5〜10 倍** になる領域です。

## 適用しないタイミング

- 個人体験のみで構成され、リポジトリの状態に依存しない記事（運用手順・思考プロセス・ワークフロー記事）
- 公開ライブラリの一般的な使い方の記事（公式ドキュメントが一次情報）
