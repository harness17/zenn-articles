## タイトル

AIとの設計判断をMy-Skill-Graphに残して再利用する

## 想定読者

Codex や Claude Code を使っているが、会話ごとに設計判断や記事の切り口が散らばり、後から同じ判断を説明し直すことに困っている個人開発者。

## 記事の核

この記事は、AI 同士のクロスレビュー運用ではなく、**AI との作業で生まれた設計判断を会話ログから切り出し、次の実装・記事・ポートフォリオ説明に再利用する運用**に絞る。

## 1番記事との差分

| 記事 | 中心 | 扱うもの | 扱わないもの |
| --- | --- | --- | --- |
| `ai-cross-review-handoff-workflow` | レビュー品質 | 作成者とレビュアーを分ける、公開前ゲート、実際に拾えた指摘 | 設計判断ノートの運用 |
| 本記事 | 判断の再利用 | `decisions/`、`strategies/`、命題文タイトル、記事候補への転用 | クロスレビューの検出事例一覧 |

## 方針チェック

- **詰まったポイント**: AI との会話ログに判断理由が埋もれ、数日後に「なぜそうしたか」を探し直す必要があった
- **解決の判断軸**: 全ログ保存ではなく、後で説明したい判断だけを命題文ノートに圧縮する
- **実例**: 設計判断ノート、戦略メモ、Zenn 記事候補の切り分け
- **書かないこと**: Obsidian 入門、AI ツール比較、クロスレビュー指摘事例の詳細

## 構成

### はじめに（300〜400字）

- Codex / Claude Code で作業速度は上がった
- ただし、会話ログに判断理由が埋もれる問題が出た
- My-Skill-Graph を「ログ置き場」ではなく「判断再利用の置き場」として使う

### セクション1: 会話ログから判断だけを探すのは重かった（500〜700字）

- 伝えること: 会話ログは過程を残せるが、次の作業で使いたい情報を探すには細かすぎる
- 具体例:
  - 記事候補の採用理由
  - 設計の代替案
  - 次に同じ判断を使う場面

### セクション2: decisions には「なぜ選んだか」を置く（800〜1000字）

- 伝えること: 技術名ではなく命題文で判断を残す
- 具体例:
  - `入力フォームをViewModelに寄せたのは画面都合をEntityへ混ぜないため`
  - frontmatter の `alternatives` / `rationale`
- コード例: decision note の Markdown

### セクション3: strategies には技術判断がどう使えるかを置く（700〜900字）

- 伝えること: 設計判断を記事、OSS、仕事探しの説明材料につなげる
- 具体例:
  - クロスレビュー記事とは分ける判断
  - 本記事の切り口を「ツール紹介」ではなく「判断の再利用」に寄せたこと
- コード例: strategy note の Markdown

### セクション4: 記録する条件を決めないと続かない（500〜700字）

- 伝えること: すべてを記録しない。後で説明したい判断だけ残す
- 具体例:
  - 残す: 代替案比較、新パターン採用、記事戦略への接続
  - 残さない: 誤字修正、フォーマット、単純なファイル読み取り

### セクション5: 記事候補を探すときに判断メモが効いた（500〜700字）

- 伝えること: 記事候補はゼロから探すのではなく、過去の判断から拾う
- 具体例:
  - YouTube Data API クォータ対策
  - ASP.NET Core MVC の ViewModel 分割
  - My-Skill-Graph 運用自体

### セクション6: クロスレビュー記事とは役割を分ける（300〜500字）

- 伝えること: 1番記事との重複を避けるため、レビュー検出事例は深掘りしない
- 具体例:
  - クロスレビュー運用: 別 AI で何を検出できたか
  - 設計判断メモ運用: 検出や実装から生まれた判断をどう再利用するか

### まとめ（150〜250字）

- 要点:
  - 会話ログだけでは判断の再利用に向かない
  - 命題文タイトルで `decisions/` に残す
  - 記事やポートフォリオに使える示唆は `strategies/` に分ける
