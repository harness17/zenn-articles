# Qiita構成メモ: AIに「修正して」と頼むと無関係コードまで整形される問題に Surgical Changes ルールで対処した

## 中心主張（1文）

AI コーディングエージェントに修正を頼むと、依頼範囲外の隣接コード・フォーマット・コメントまで「改善」されて差分が膨らむので、Karpathy の Surgical Changes 原則を 1 枚のルールに書いて先渡しすると差分が依頼に直結するようになる。

## 想定読者

- Claude Code / Codex / Cursor などで修正依頼すると関係ないコードまで触られる経験がある人
- AI が生成する diff が大きすぎてレビューが大変な人
- AI のリファクタ意欲を抑える明確なルールが欲しい人

## 詰まったポイント

- 「ここの引数を 1 つ追加して」と頼んだら隣の関数のフォーマットも勝手に整えられた
- 「バグだけ直して」と頼んだら関係ない dead code を削除された（後で必要だった）
- 「import を 1 つ追加して」と頼んだら未使用と判断された import まで一緒に消された
- diff が膨らみすぎて、修正が依頼通りかどうかのレビューにコストがかかる

## 採用したルール（先渡しテキスト）

karpathy が指摘している原則を、1 つのルールファイル `karpathy-coding-principles.md` にまとめて CLAUDE.md / AGENTS.md から先に読ませる。中心は「Surgical Changes（外科的変更）」セクション。

```markdown
## Surgical Changes（外科的変更）

**触るのは必要な箇所だけ。自分が作ったゴミだけ片付ける。**

既存コードを編集するとき：
- 隣接コード・コメント・フォーマットを「改善」しない
- 壊れていないものをリファクタしない
- 既存スタイルに合わせる（自分なら違う書き方をしても）
- 関係ない dead code を見つけたら**削除せず言及する**

自分の変更が orphan を生んだとき：
- 自分の変更で不要になった import / 変数 / 関数は削除する
- 以前から存在する dead code は触らない

**テスト**: 変更した行がすべてユーザーのリクエストに直結しているか？
```

## このルールが効く理由

- 「触らない範囲」を明示すると、AI の「親切に直してあげよう」が止まる
- 「自分が作ったゴミだけ片付ける」と書くことで、orphan import 削除と既存 dead code 削除を区別できる
- 最後の「変更した行がすべて依頼に直結しているか」が自己チェックの問いになる

## 落とし穴

- 「Surgical Changes」だけだと不要機能追加は防げないので、同じファイル内に「Simplicity First（頼まれていない機能を書かない）」も並べる
- 既存スタイルが本当に悪い時は別タスクで明示的にリファクタを依頼する
- AI レビュー時の指摘も同じルールに従わせる（レビュー側も「ここも直すべき」と無関係指摘をしがち）

## 実運用での変化

- 1 タスクあたりの diff 行数が体感で半分以下
- 関係ないファイルが Modified に出てこない
- 「これ依頼してないけど触られた」を発見する回数が減った

## まとめ（記事末尾用）

- AI の diff が膨らむ問題は「触らない範囲」を明示するルールで抑える
- 1 ファイル 1 ルール（Surgical Changes）として CLAUDE.md から import して常時適用
- 「変更した行がすべて依頼に直結しているか」を自己チェックの問いとして書く
