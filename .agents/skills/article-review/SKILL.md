# article-review

`articles/<slug>.md` を公開前に検査する。レビューだけの依頼では指摘を表形式で出し、修正は自動でしない。ユーザーが「レビュー対応」「コメント対応」「直して」と明示した場合は、対象コメントを分類して最小修正する。

## 起動条件

- ユーザーが「記事をレビュー」「公開前チェック」「推敲」と言ったとき
- ユーザーが「レビュー対応」「コメント対応」「指摘を直して」と言ったとき
- フロントマターを `published: true` に変更しようとしているとき
- `/article-review` で呼ばれたとき

## チェック項目

### 1. フロントマター

| 項目 | 必須/推奨 | チェック内容 |
|------|---------|------------|
| title | 必須 | 30〜40字、検索キーワード含む |
| emoji | 必須 | 設定済みか |
| type | 必須 | `tech` または `idea` |
| topics | 必須 | 1〜5個、英小文字 |
| published | 必須 | 公開直前のみ `true` |

### 2. 文体ルール違反語スキャン

以下の語を grep し、ヒットしたら行番号と該当箇所を表示：

```
NG語リスト（@.Codex/rules/writing-style.md と同期）:
- 素晴らしい / 驚くべき / 画期的 / 魔法のように
- いかがでしたでしょうか / いかがだったでしょうか
- ぜひ参考にしてみてください / ご参考になれば幸いです
- 〜とされている / 〜と言われている（一次情報なら断言する）
- 皆さんも試してみてください
```

`〜ing 連鎖`（同じ段落内で「〜することで」が3回以上）も検出する。

### 3. 必須要素チェック

| 要素 | 検出方法 |
|------|---------|
| GitHub リポジトリへのリンク | `github.com/harness17/` を本文に含むか |
| 実コード（5行以上） | コードブロックの最大行数を計測 |
| 自分の体験・失敗例 | 「実際に〜した」「〜で失敗した」等の体験表現があるか（手動確認） |
| 文字数 | 2000字以上か |

### 4. 守秘義務チェック

以下のキーワードに該当する固有名詞が含まれていないか：

- 過去勤務先名（トランスワード、プロアクティブ）
- 顧客名（ボートレース下関、旅行業の固有社名 等）
- 同僚・関係者の実名

該当があったら必ず指摘する。一般化を提案する。

### 5. 構成チェック

- 「はじめに」「まとめ」セクションがあるか
- 見出しが3〜5個か
- コードブロックに言語指定があるか（` ``` ` だけのブロックは検出）
- JavaScript のコードブロックは `javascript` より `js` を優先し、実ファイル由来の例なら ` ```js:fetcher.js ` のようにファイル名を付ける
- URL だけのコードブロックは `text` のまま放置せず、直前に「URL は次の形式」のような説明を置くか、`http` など意図が伝わる言語指定にする
- 参照表記の一貫性: 同じ過去記事・ツール・概念が記事内の複数箇所（本文・冒頭リスト・参考リンク）に出るとき、表記が揺れていないか。特に過去記事タイトルは、参考リンクの実タイトルと本文中の言及で食い違うと別記事に見える。揺れていたら、実タイトルへ統一するか、リンク先が同一であることが分かる記述に揃えるよう指摘する
- 前提知識の補足: 記事固有の前提となるツール名・サービス名（例: Codex、Claude Code）が初出する箇所で、読者が何を指すか分かる程度の説明があるか。文脈で推測可能でも、初出時の一文補足で前提知識の差を埋められる場合は指摘する

### 6. Zenn記法チェック

- 重要な注意点、制約、配布時のハードルは通常の箇条書きだけで流さず、必要に応じて `:::message` または `:::message alert` で強調する
- 補足的な長い手順や背景説明は、本文の流れを止める場合に `:::details タイトル` で折りたたむことを検討する
- ただし、Zenn記法は強調したい箇所に限定し、1記事内で多用しすぎない

### 7. 相互レビューゲート

- 作成者が Codex の場合、ClaudeCode へのレビュー依頼またはレビュー結果が `CLAUDE_CODE_HANDOFF.md` に残っているか
- 作成者が ClaudeCode の場合、Codex へのレビュー依頼またはレビュー結果が `CLAUDE_CODE_HANDOFF.md` に残っているか
- 継続作業に関わる場合、My-Skill-Graph の `ops/handoffs/` または `self/goals.md` に次アクションが残っているか
- `published: true` への変更は、相互レビュー記録とユーザーの公開指示が揃うまで止める

### 8. 中心主張の事実整合チェック（@.claude/rules/article-fact-check.md と同期）

個人開発リポジトリの実コードに言及する記事は、以下を確認する：

- 「A には X しかない」「A は Y 非依存」「A→B で新規追加」のような断言を含む記事は、`gh api` でファイル全体・依存リスト・コミット履歴を確認したか
- 参考リンクの `blob/<branch>` 部分は、`gh api repos/<owner>/<repo> --jq '.default_branch'` で確認したブランチ名と一致するか
- csproj / package.json / requirements.txt の `<PackageReference>` / `dependencies` を確認したか
- 二世代比較記事は、両世代の実体を**両方とも全範囲で**確認したか（`head -60` で済ませない）

M 記事執筆で 3 回連続の事実誤認を踏んだ反省から追加した観点。中心主張の事実誤認は公開後の修正コストが極めて高いため、機械チェックを優先する。

## レビューコメント対応モード

ユーザーがレビューコメントを貼って「対応して」と依頼した場合は、次の順で処理する。

1. コメントを分類する
   - 技術的誤り・リンク確認・記法修正: 原則対応する
   - 読者向け補足: 本文の流れを崩さない範囲で1〜2文だけ足す
   - 講評・称賛・任意改善: 本文へ取り込まない
2. 外部ツールや現在性のある情報への指摘は一次情報で確認する
   - CLI、公式ドキュメント、GitHubリポジトリ、ライブラリ状態などは現在変わり得るため、公式情報または対象リポジトリで確認してから直す
3. コード例への指摘は、読者がコピーしたときのコンパイル・実行単位を意識する
   - 抜粋で省いた `using`、ファイル名付きコードブロック、Zenn の `言語:ファイル名` 記法を優先して直す
4. NG語の例示は、文体スキャンを壊さない表現に丸める
   - 例: 禁止語そのものを長い引用で残さず、「〜系の締め」「問いかけ型の締め」のように言い換える
5. 修正後に必ず確認する
   - 対象コメントの該当箇所
   - 文体NG語スキャン
   - `git diff -- <対象記事>` で差分がコメント対応に収まっているか

## やらないこと

- 自動修正（ユーザーが判断する）
- 内容の意味的レビュー（事実誤認は別途、アドバイザーモデルで確認する）

## 完了条件

- すべてのチェック項目について結果を報告した
- 公開可否判断（🟢 / 🟡 / 🔴）を提示した
- 相互レビュー記録の有無を報告した
