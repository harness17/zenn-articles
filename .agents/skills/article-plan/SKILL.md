# article-plan

新しい Zenn 技術記事の企画・構成を行う。出力は `drafts/<slug>.md` に保存し、執筆 Phase 2 までの成果物を作る。

## 軸となる方針

**「課題解決力ベース・体験記事優先」**（@.Codex/rules/topic-policy.md と同期）。

- 「実際に詰まって、自分で考えて、こう解決した」体験を持つ記事を優先
- 網羅的な解説記事（「〇〇テクニック5選」等）は書かない
- 解決の判断軸が言語化されているか、必ず確認する

このスキルは、ユーザーが提案するテーマがこの方針から外れているとき、**指摘して再考を促す**。

## 起動条件

- ユーザーが「新しい記事を書きたい」「次の記事は〜」「構成を考えて」と言ったとき
- 既存の `drafts/<slug>.md` を更新したいとき
- `/article-plan` をスラッシュコマンドで呼ばれたとき

## 実行ステップ

### 0. 候補と既存記事の照合

テーマを提案する前に `drafts/article-candidates.md` を確認する。

- `公開済み` / `公開指定済み / Zenn未確認` / `下書きあり` の候補を重複して提案しない
- 既存記事と近いテーマは、差分が明確に言える場合だけ候補に残す
- 新しい構成メモを作成または更新したら、対応候補を `下書きあり` に更新する
- 候補外の派生記事を作る場合も、`drafts/article-candidates.md` の `既存記事リスト` または候補対応表に追記できる形で slug と主題を残す

### 1. テーマ確認（質問する）

推奨候補（H〜R、@.Codex/rules/topic-policy.md と `drafts/article-candidates.md` に詳細）を念頭に、ユーザーから次を引き出す：

- どのテーマか（候補H〜Rの番号 または 自由記述）
- 具体的なサブトピック
- **「詰まったポイント」と「解決の判断軸」が言語化できるか**（ここが言えなければ別候補に切り替え）

Codex.local.md に「第1記事 = 候補H（YouTube Data API クォータ枯渇）」と書かれているため、第1記事は候補Hを起点に提案する。

### 1.5. 方針チェック（必ず行う）

ユーザーが提案するテーマが以下のどちらかに当てはまるかを確認する：

| OK パターン | NG パターン |
|------------|------------|
| 「YouTube API のクォータが枯渇して困った」→ 詰まり明確 | 「SQL Server チューニング 5選」→ 体験ではなく網羅 |
| 「Phycock で2テーブルを統合した判断」→ 判断軸明確 | 「ASP.NET Core 10 とは」→ 解説記事 |
| 「SmartScreen でユーザーが警告された」→ 課題明確 | 「設計パターン入門」→ 体験不在 |

NG パターンに該当するときは、書ける体験があるか掘り下げる。なければ候補H〜Rに誘導する。

### 2. 想定読者を1文で言語化

「〇〇な△△エンジニア」のように具体化する。曖昧な「みんな」は禁止。

### 2.5. 読者前提と用語補足を先に決める

LAPRAS AI レビューで明確性が 3.5 前後に留まりやすい。コマンド例や作業フローが明確でも、初心者向けの背景説明と「なぜ重要か」の動機付けが薄いと読者層によって理解に差が出る。構成段階で次を決める。

- 対象読者が既に知っている前提と、本文で補足する前提を分ける
- 初出で説明すべき用語を列挙する（例: OAuth / RSS / YouTube Data API / Identity / handoff / ハーネス化）
- 「なぜこの仕組みが必要か」を初心者にも伝わる問題設定として 1 段落分用意する
- 読者がこの運用を怠ると何に困るか、逆に導入後に何が改善するかを1文ずつ用意する
- 採用しなかった選択肢と、その理由を最低1つ用意する
- 近接する既存記事がある場合は、本文中で役割分担を説明する位置を決める

### 3. 見出し3〜5個を提案

各見出しで以下を箇条書き化：
- 何を伝えるか（1文）
- どんな具体例を出すか（コード／図／実体験のどれか）
- 想定文字数
- 前後セクションとの橋渡し文が必要か

関係性やトレードオフが中心になる記事では、図または表を 1 つ検討する。

- `decisions` / `strategies` のような概念関係: Mermaid 図
- RSS / API、簡易 / フルモードのような比較: 表
- 導入後に詰まる運用: トラブルシューティング小セクション
- 配布や公開が絡む記事: 実装判断から配布課題へ移る橋渡し文

### 4. コード例の準備リスト

各セクションで使うコード例を表で整理：

| セクション | コード言語 | 出典 | 準備状況 |
|----------|----------|------|---------|
| 例：履歴管理テーブル | SQL | DevNext から引用 | 未着手 |

### 5. drafts/<slug>.md に書き出し

スラッグは英数小文字とハイフン。例：`youtube-data-api-quota-exhaustion`、`phycock-schedule-merge`。

ファイル構成：

```markdown
# <記事タイトル案>

## メタ情報
- type: tech
- topics: [tag1, tag2, ...]
- 想定文字数: 2500〜3500字
- 想定執筆時間: 6〜8時間
- ステータス: 構成中 / 執筆中 / 推敲中

## 想定読者
（1文で）

## 読者前提と補足する用語
- 既知として扱うこと:
- 本文で補足する用語:
- 初心者向け問題設定:
- なぜ重要か:
- 採用しなかった選択肢:
- 導入後に確認できる改善:

## 構成

### はじめに（200〜300字）
- 何の記事か
- 誰に読んでほしいか
- 何が分かるか
- 初出用語の短い補足

### 本論セクション1: <見出し>
- 伝えること:
- 具体例:
- 想定文字数:
- 前後の接続:

### 本論セクション2: ...

### まとめ（150〜250字）
- 要点3つ

## コード例の準備状況
（表）

## 図表・比較表の予定
- 概念関係図:
- トレードオフ表:
- 導入後の詰まりどころ:

## 参考リンク候補
- 公式ドキュメント
- 関連リポジトリ（DevNext など）
```

## 守ること

- 文体ルール（@.Codex/rules/writing-style.md）に違反しない見出し案を提案する
- 守秘義務に触れる業務情報（顧客名・案件名）は構成メモにも書かない
- 個人開発リポジトリ（DevNext など）の言及方針は Codex.local.md の表に従う
- **個人開発リポジトリの実コードに言及する記事は、構成案を出す前に @.claude/rules/article-fact-check.md のチェックリストを通す**。特に「中心主張のファイル全体確認」「csproj / package.json の依存確認」「ユーザーへの軸絞り込み質問前の事実裏取り」は必須
- ユーザーへの軸絞り込み選択肢を提示する前に、各選択肢が**実コードに存在するか**を `gh api` 等で確認する。存在しない選択肢を出題しない（M 記事執筆で「BaseController 系の多重 Generic」を選ばせたが実コードに存在せず軸破綻した反省）

## 完了条件

- `drafts/<slug>.md` が作成または更新された
- 対応する候補状態が `drafts/article-candidates.md` で確認または更新された
- ユーザーが構成案にOKを出した
- 次のアクション（執筆開始 or さらに構成練り直し）が明確になっている
